## 执行摘要

公司自动化系统是一套**「确定性治理外壳 + 委派式模型内核」的双平面架构**，工程质量高、安全边界扎实（149 个单元测试全绿、幂等/退避/死信/自愈齐备、对未知成本与未计量价值坚持不造假），但**智能化被刻意约束在"可执行、不可决策"的层面**。

一句话结论：**系统很会"干活"，也很会"记账"，但几乎不"做决定"——所有真正的经营判断都卡在人肉审批环节。**

三个最关键的量化事实：

| 信号 | 数值 | 含义 |
|------|------|------|
| 待审批 P0 提案积压 | **3 条，最老 8 天**（2026-07-20 起） | 治理回路产出提案的速度 > 人批准的速度 |
| 已完成运行「无业务结果」比例 | **约 78%（64/82）** | 系统看不见自己是否创造了价值（价值反馈断裂） |
| 自治经营执行器状态 | **⏸️ 已暂停**（等 07-27 起的"工具 vs 真经营"裁决） | 唯一的主动执行入口被一个未决的元决策整体冻结 |

> 智能化的瓶颈不在"模型不够强"，而在**决策权 100% 保留给人、价值反馈回路缺失**。这两点互为因果，形成"证据不足 → 人不敢批 → 积压 → 回路空转"的恶性循环。

## 一、智能化架构总览

### 1.1 用到了哪些 AI / Agent 能力

| 能力 | 角色 | 接入方式 | 真实使用度 |
|------|------|----------|:---:|
| **Hermes Agent** | 编排中枢 + 对话主 Agent + 隔离一次性 Worker | `pre_llm_call` Shell Hook + `hermes chat -q <prompt>` 子进程 | 🟢 核心 |
| **Swarm 蜂群**（swarm-knowledge） | 安全分析并行 analyst/reporter Worker | `swarmctl.py task submit` 子进程 | 🟢 安全线主力 |
| **Codex / Claude Code** | 原生会话，用于**用量与成本核算**；每日 auto-fix 备援执行 | 读取 `~/.codex/**/rollout-*.jsonl`、`~/.claude/projects/**/*.jsonl` | 🟡 记账为主 |
| **TVCR Agent** | 独立经营分析（Time/Value/Cost/Risk）→ 结构化提案 | 隔离 `hermes chat` + 确定性输出校验 | 🟢 治理核心 |
| **内容 Worker**（article/video/company） | 撰写/去 AI 味/自检/排版；视频脚本分镜 | 最小权限 `hermes chat`（仅 file/web/image/vision 工具集 + humanizer 技能） | 🟢 内容线主力 |
| **AgentKey / AnySearch** | 市场雷达外部公开检索适配器 | 固定 commit + ZIP 哈希的 JSON-RPC 适配器 | 🟢 雷达采集 |
| **Agency Agents（233 代理池）** | 按 12 分部映射公司部门的专家代理 | `agency_agents_search/delegate` | 🔴 名义资产，实际低频 |

**关键观察**：全仓约 7,800 行核心代码里，真正的"模型调用点"只有 **6 处** `subprocess.run(["hermes"/"swarmctl", ...])`。这个比例（数千行确定性编排 : 一小把 LLM 调用点）本身就是"规则重、模型轻"最直接的量化证据。所谓"233 个代理"是插件目录容量，`agent-roster.md` 自述的实际用途仅集中在文章撰写与 QA，并非活跃的多代理协同。

### 1.2 能力之间如何协作

```
用户消息
  │  Hermes pre_llm_call Hook
  ▼
company_router.py ──分类(纯正则/关键词)──▶ ┌─ security → swarmctl 蜂群
  │  幂等/去重/授权门/会话来源鉴别            ├─ article/video/company → 隔离内容 Worker
  │                                          └─ 问答/低置信 → 主 Agent 自己答
  ▼
后台 Run ──company_result_notifier(每1分钟)──▶ 轮询/Runner自愈/退避投递/死信 → 微信回传
  │
  ├─ company_daily_digest(09:00 只读) ──▶ notification_outbox ──▶ 管理者日报
  ├─ market_radar(08:30) ──▶ 打分/去重/多源佐证 ──▶ market_pulse
  └─ tvcr_daily_review ──▶ 确定性证据包 ──▶ TVCR Agent 分析 ──▶ proposals.json
                                              │ validate_outputs(确定性校验)
                                              ▼
                                   improvement_proposals(pending_approval)
                                              │  ★人肉审批★ (在聊天里打"批准 TVCR-P-…")
                                              ▼
                                   operating_experiments(planned→running→…)
                                              │  主 Agent（人触发的对话）落实
                                              ▼
                                   company_operator(⏸️暂停) / company_auto_fix_guard(每日自修复)
```

协作的骨架是**事件驱动的确定性流水线**：Hook 触发路由，路由派发 Worker，Notifier 回传，Digest 汇报，TVCR 评估，人审批，实验落地。模型只在"叶子节点"被调用去完成一次具体认知任务，其输出**从不被直接信任**——一律经确定性校验（缺文件即失败、`result.json` schema 校验、`validate_outputs` 拦截"价值=0"类记账谬误、安全线 no-findings 抑制、财务须附 SHA256 证据）。

### 1.3 智能化深度：规则驱动 vs 模型驱动 vs 混合

**结论：混合，但决策/编排层几乎纯规则，执行层才交给模型。**

- **控制平面（规则驱动，~95% 代码量）**：路由分类、去重幂等、机会打分、市场信号加权、财务记账、TVCR 证据聚合、输出校验、通知退避/死信、实验状态机——全部固定规则 + 参数化启发式，无语义理解，有 149 个测试兜底。
- **执行平面（模型驱动，~6 个调用点）**：文章创作与自检、安全分析、TVCR 经营推理、自治机会执行——真正的"思考"在此，但被最小权限工具集、强制产物、确定性校验三重护栏包住。

用一句话定位：这是**"受治理的有界 Agentic"（governed bounded-agentic）**——安全、可核验、可回滚，但智能被刻意关在笼子里，且**没有任何模块形成"模型输出→真实反馈→自我改进"的闭环**（详见第二节评分，无一模块达到 5 分）。

## 二、各模块智能化评级

**评分标尺（1–5，衡量"智能化/自主决策程度"，非代码质量）：**
`1` 纯确定性管道/记账（确定性本身即设计目标）｜`2` 规则引擎+参数化启发式，无语义理解｜`3` 规则编排+模型执行混合，或有自治回路但受限/暂停｜`4` 核心决策由模型推理/生成驱动，带确定性护栏｜`5` 模型驱动 **且** 有闭环反馈/自学习

| 模块 | 评分 | 定位 | 判据 |
|------|:---:|------|------|
| `company_router.py` | **2/5** | 任务分发路由 | 分类纯 `regex`+关键词（`classify_message`），fail-closed 门禁做得很细，但对措辞脆弱、无语义理解；低置信直接退回主 Agent 而非兜底 |
| `company_operator.py` | **3/5** | 自治经营执行 | 全系统唯一主动回路：多源机会发现 + 固定优先级打分(`P0=100…`)+ 龄期加权 + 轮询公平 + 风险门；执行委派 Hermes Worker。**但当前整体暂停** |
| `company_daily_digest.py` | **1/5** | 日报生成 | 纯 SQL 聚合 → 模板拼字符串，零模型。确定性正确，但毫无"智能" |
| `company_result_notifier.py` | **1/5** | 结果通知 | 轮询/自愈/退避/死信/outbox，1,146 行硬核可靠性工程，但无任何模型决策 |
| `company_auto_fix_guard.py` | **1/5（守卫）/ 3（整条自修复回路）** | 自动修复 | 守卫本身是确定性 worktree 隔离预检；真正修 bug 的是每日 agent（git log 见 8 次 auto-fix 提交），回路层面算模型驱动自修复 |
| `finance_ledger.py` | **1/5** | 财务记账 | 证据化记账、预测/实收隔离、未定价显式保留。**故意零智能**，这是正确的——账不该"聪明" |
| `operations_control.py` | **2/5** | 运营控制/治理状态机 | Run 同步(读原生日志)、结果回填、提案导入、实验生命周期、`apply_user_decision` 用正则解析"批准/拒绝"。编排确定，智能外包给 TVCR Agent |
| **TVCR 提案治理** | **4/5（分析）/ 3（闭环）** | 经营治理 | 独立 Agent 对 T/V/C/R 真推理并产结构化提案，且有确定性校验拦截记账谬误——分析确有智能。但**审批 100% 人肉、近 6 次复盘 2 次 failed(≈33%)、提案积压**，闭环被拖到 3 |
| **市场雷达** | **2/5** | 外部信号发现 | `score_signal` 固定权重加权(相关/商业/新鲜/信源−风险)+阈值资格门+多源佐证；采集靠外部检索。打分无语义模型，下游语义核验属（已暂停的）operator |
| **内容生产管线** | **4/5** | 文章/视频产线 | 生成与"去 AI 味"、3–4 道 QA Gate 全由模型驱动，含 humanizer 技能、最小权限、强制产物。但 QA 是**模型自评**（弱信号），发布仍人工 |

**评分分布的信号**：无一模块达到 5 分——因为**全系统没有"真实反馈→自我改进"的闭环**。得高分(4)的都是"单次认知很强"的执行/分析模块，得低分(1–2)的都是刻意确定性的管道与记账（对它们而言 1 分是褒义）。真正被"人肉决策"拖累评分的是 TVCR 与内容线（分析/生成 4，闭环掉到 3）。

## 四、关键瓶颈

### 4.1 最大的智能化断层：**决策权全留给人**

架构能"感知（雷达/日报）→ 分析（TVCR）→ 提议（proposals）→ 执行（Worker）"，唯独**不能"决策"**。TVCR 的定位被严格限制为"经营分析委员会，不改生产系统"，`company_operator` 只能跑 `risk_level=low` 的内部任务。于是**每一个跨越阈值的判断都必须回到人**，而人是一个低带宽、异步、会疲劳的节点。这是规则驱动系统的天花板：规则能编排一切"怎么做"，但回答不了"该不该做、值不值得"。

### 4.2 拖累效率的"人肉决策"节点

1. **提案审批**（最痛）：治理回路每日产提案，人批准是唯一出口 → 直接造成 P0 积压。
2. **业务结果补录**：78% 运行无结果 → TVCR 的 ROI 分析建立在残缺证据上 → 提案质量打折 → 人更不敢批。
3. **战略元决策未决**：整条自治线因一个"工具 vs 经营"的裁决而**整体暂停**，一个未回答的问题冻结了一整个子系统。
4. **成本定价**：63 个 unpriced 会话使"投入"侧长期不完整，任何 ROI 判断都悬空。

### 4.3 3 条 P0 积压超 72 小时，反映了什么

不是"人懒"，而是**三层结构性问题**：

- **吞吐失配**：自动化产出提案的速度 > 人审批速度，且系统**没有为决策设计任何加速/分流机制**（无自动批准策略、无 SLA 升级、无按风险分级的差异化门槛）。日报只会"提醒 stale"，但提醒不产生动作。
- **证据不足以支撑决策**：因为 78% 结果 `unmeasured`、成本未定价，人面对提案时**缺少批准所需的价值证据**，于是理性地选择"再等等"→ 积压。**这才是根因：不是审批慢，是反馈回路断裂让审批无从下手。**
- **元决策阻塞判据**："真经营 vs 工具"未定，意味着"什么样的提案该批"这个**判断标准本身缺失**，任何单条提案都无法被自信地裁决。

> 一句话：P0 积压是"**价值反馈缺失 × 决策权集中 × 判据未定**"三者叠加的可观测症状，而非孤立的人效问题。

## 五、改进建议

### 5.1 低投入高回报（可立即做）

1. **自动闭合"结果回路"**（最高杠杆）：`backfill_outcomes` 已存在，但只从有限来源回填。扩展它去读**已有的** `article_performance.db` / 公众号阅读数 / 发布状态，确定性地自动补录 accepted/published/reach——把 78% 的 unmeasured 直接砍下来。这是解开"证据不足→不敢批"死结的第一刀，且不需要新模型能力。
2. **提案分级审批 + SLA**：对 `P2/低风险、且 change_scopes 落在已批准范围内`的提案，允许**策略化自动批准**（或对 process/resource 层设"常备授权"），把人的注意力集中到 P0/外部动作。为 P0>72h 增加**自动升级/自动过期-supersede**，让日报的 stale 提醒变成真实动作而非只读文字。
3. **路由器低置信 LLM 兜底**：`classify_message` 置信 <0.5 时目前直接退回主 Agent（等于放弃自动化）。改为**触发一次廉价 LLM 分类**再决定——一次 Hermes 调用，把误路由/漏路由变成正确路由，显著抬升路由准确率。
4. **执行可靠性清理**：为 `operational_runs` 增加**卡死回收**（复用 router 的 `stale_run_minutes` 思路处理 14 条 `running`）；在日报里对失败做**聚类**，让每日 auto-fix agent 精准打击 Top 失败类别，把 25% 失败率压下去。
5. **补齐 63 个 unpriced 会话定价**：25 条报价已入库，把"模型→实际成本"映射接通（本就是 DASHBOARD 列出的里程碑），让 ROI 不再建立在隐性 $0 基础上。

### 5.2 需要架构级改造

1. **决策支持 / 策略化审批引擎**：把用户的风险偏好与"工具 vs 经营"裁决**编码为策略**，让一类决策由策略（+模型辅助）自动做出，人只兜底 P0/外部/不可逆。**这是抬升"人肉审批天花板"的唯一根本解**——先逼出战略裁决，让审批**判据**存在，再用策略引擎放大它。
2. **建真实反馈回路 / 价值模型**：把市场/读者/收入信号接回作为"奖励信号"；把 QA Gate 从**模型自评**升级为"确定性检查 + 独立评估 Agent + 真实互动指标"三源合一。这一步把内容/安全线从**开环**变成**闭环学习**，也是让评分从 4 迈向 5 的唯一路径。
3. **决策/打分层引入模型**：用 LLM/嵌入层增强或替换路由的正则分类、雷达的固定权重打分、operator 的机会选择（确定性门禁保留为安全网）。系统性抬高 router+雷达+operator 三处的"智能地板"。
4. **让学习复利**：swarm-knowledge DIKW 已存在但晋升 5 道门全人工（64/66 阻断）。为**非敏感的运营经验**开一条"受治理但自动"的晋升通道，让系统跨任务/跨天复利，而不是每天从零推导。
