## 一句话总结

用 AI 做漏洞挖掘，关键不是模型有多强，而是你怎么用它——逐文件扫描的本地小模型吊打了烧 6000 万 token 的云端全自动方案。

## 为什么选这篇

国内关于「AI + 安全」的讨论有个很典型的分裂：一边是安全厂商拿AI当营销噱头，另一边是研究员嫌AI不够靠谱、产出太水。真正坐下来做对照实验、把四种方案拉出来跑分、给出真金白银成本数据的文章，凤毛麟角。

Eddie Zhang 在 Project Black 干的这件事很实在：拿一个已知漏洞当基准，四种方案逐一对标，把钱和时间都晒出来。更妙的是，他用的是哈希猫密码破解机的旧硬件跑的本地模型——这对国内动不动就「没 H100 干不了 AI」的焦虑是一记清醒的反驳。

## 核心观点

**观点一：拼模型不如拼方法。** 烧了 6000 万 token 的云端 AI 代理（GLM 5.1 + Strix）跑了 12 小时没找到漏洞，而本地 Qwen 3.6 27b 配合逐文件扫描的定制 harness 每次都能找到。差距不在模型，在工程架构。

**观点二：全自动 ≠ 更靠谱。** Strix 的全自动 AI 渗透测试看起来很酷——自己 clone 仓库、自己装环境、自己写报告——但它漏掉了目标漏洞，反而报了一堆误报。有工程约束的自动化比没约束的全自动更可靠。

**观点三：本地模型在单文件代码审查上足够用了。** 把整个代码库塞给一个 Agent 让它通读，几乎所有模型都会拒绝或漏掉关键路径。但换成「一次一个文件 + 上下文」，Qwen 3.6 27b 就是在 800 个源文件上稳定输出。

**观点四：这条路径已经能挖真 0day 了。** 不只是基准测试跑得漂亮，同一个 harness 在上线后顺手挖到了 myVesta 的认证 RCE（CVE-2026-12195），一个能打到 web 服务器管理面板权限的真实漏洞。

## 深度解读

### 基准漏洞：一个教科书级的 LFI

Eddie 选的基准漏洞是 PHPIPAM 里的认证本地文件包含（LFI），CVE-2026-12194。很简单：用户输入的 controller 名直接拼进 `require_once`，没有任何过滤。只要开了 API（默认关闭）且有有效凭据，就能包含任意 .php 文件。

选这个漏洞很聪明——不够危险所以厂商不急着修（实际也确实没回应），但够典型所以能看出每种方法的搜索能力。

用一张表来看四种方案的结论：

| 方案 | 找到漏洞了？ | 成本 |
|------|:---:|------|
| Semgrep 自动扫描 | ❌ 没找到 | 免费 |
| GLM 5.1 + Strix AI Agent | ❌ 没找到 | ~$30（6000万token） |
| Cloud SOTA + Code Review Skill | ⚠️ 有时候 | $5-10/次 |
| 本地 AI + 定制 Harness | ✅ 每次都能 | 硬件折旧 |

### 方案一：Semgrep —— 老牌 SAST 的天然天花板

`semgrep scan --config auto` 没扫出来。这不是 Semgrep 的错——传统 SAST 工具的问题从来都是「你只能写你已经知道存在的危险模式的规则」。对于没见过的新漏洞模式，规则库就是盲区。

### 方案二：Strix + GLM 5.1 —— 12 小时和 $30 打了水漂

这是最戏剧性的结果。Strix 是个全自动 AI 渗透测试框架，GitHub 25000+ star，文档推荐用 GPT-5.4、Claude Sonnet 4.6 或 Gemini 3 Pro。Eddie 不想烧大模型的钱，用了更便宜的 GLM 5.1 来观察 token 消耗。

12 小时后，6000 万 token，$30（部分请求走了免费推理），一份 `report.md` 出炉。对标的 LFI 没找到。报告里列了一堆其他发现——敏感数据暴露、存储 XSS、SSRF、越权、CSRF、SQL 注入——但仔细一看，有些是 PHPIPAM 设计如此，有些是误报，有些早就修了。

如果换成推荐的 Sonnet，一次就得 $180-$300。Opus 翻倍。Eddie 的结论很直白：「我不想花那个钱再试一次。」

### 方案三：Cloud SOTA + 安全审查 Skill —— 薛定谔的漏洞

这个方案用了 AI Skill（给 Agent 的 Markdown 指令文件），把漏洞类别拆分给不同子代理并行审查。结果高度不稳定——有时候能找到，有时候完全漏掉。

核心问题：在大型代码库里，审查质量取决于 Agent 读了哪些文件和它 grep 了什么关键字。一旦你手动把它指向正确文件，几乎所有模型都能立刻识别出漏洞。也就是说，瓶颈不是模型的理解能力，而是**搜索策略**。

Eddie 还发现，直接告诉 Agent「请更彻底地审查」会触发拒绝——模型判定任务太大，无法在一次 pass 中完成。即使强行让它做，成本也是天文数字。

这个洞察引出了最终赢家的核心思路：既然问题出在一次性处理整个代码库太难，那把任务拆碎，一次只给一个文件，行不行？

### 方案四：本地模型 + 定制 Harness —— 赢在工程，不是赢在模型

Harness 的逻辑朴素得惊人：

```
对每个源文件：
  → 本地模型审查单个文件（加上上下文）
  → 输出结构化报告
↓
汇总所有报告 → 人工或自动筛选
```

每次只喂一个文件给模型，模型只需要理解一小块代码。Qwen 3.6 27b 在一个跑哈希猫密码破解的旧 GPU 服务器上运行，挂着 ~170k 上下文窗口。

800 个源文件，大约 1.2 亿 token。**每次都找到了那个 LFI。**

当然也有代价：误报很多（纯代码审查的通病），对复杂越权漏洞的理解不够（缺乏应用级别的威胁建模上下文）。但至少——模型不会拒任务，不会漏掉关键文件，不会烧完预算然后交一份跑偏的报告。

### 附赠惊喜：顺手挖到 myVesta 的 RCE

基准测试刚跑完，Eddie 的朋友发来消息说遇到了 myVesta（类似 cPanel 的 web 服务器控制面板）的可疑活动。8 小时后，同一个 harness 挖出了认证 RCE——FTP 用户名删除功能里的一段遗留代码，把用户名参数直接丢进了 `exec`。

这是个能打到服务器管理面板权限的真实漏洞，CVE-2026-12195。myVesta 团队反应很快，当天就修了。Eddie 透露手里还有更多发现正在等厂商补丁窗口期。

## 我的思考

这篇文章最大的价值不是「本地 AI 能做安全」，而是它用对照实验戳破了一个流行幻觉：**更贵的模型 + 更强的自主性 = 更好的结果。**

Strix 的方案在概念上最先进——全自动，端到端，自己装环境、自己写报告——但它在具体的、可验证的目标上失败了。而那个土土的「逐文件扫描」方案反而稳定输出，不仅找到了基准漏洞，还顺手捡了个真 0day。

这对国内做 AI 工程化的团队有几个启示：

1. **不要执着于「一个模型搞定一切」。** 把大任务拆成模型擅长的小粒度任务，比找一个超强模型更重要。
2. **本地模型有真实的生产力场景。** 代码审查这种单文件、结构化输出的任务，Qwen 3.6 27b 级别就够用了。不是所有场景都需要 GPT-5。
3. **误报控制需要工程手段，不是靠模型。** Eddie 的 harness 有大量误报，但他没让模型自己审核自己（那是灾难），而是设计了一个分级验证管线。
4. **成本视角很关键。** $30 vs $300 vs 硬件折旧——如果每次审查都花几百美元，你的甲方不会买单。

说到底，这篇文章讲的不是 AI 替换人类安全研究员。它讲的是：**好的工程架构能让普通的模型做出不普通的事。**
