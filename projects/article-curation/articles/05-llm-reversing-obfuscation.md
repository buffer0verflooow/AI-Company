# LLM 逆向工程攻防战：当 Claude Opus 遇到 Tigress 混淆器

> Elastic Security Labs 在 2026 年 4 月的 ON Week 上做了个实验：让 Claude Opus 4.6 对着一堆被精心混淆过的 crackme 逆向，然后又"反向"开发了三种专门对付 LLM 自己的混淆技术。结果很有意思。

## 为什么聊这个

先说个我自己的感受。

这两年我一直在观察一个趋势：LLM 在逆向工程上的进步比大多数人想象的要快得多。我自己试过让 Claude 读过一个加了 UPX 壳的 PE 文件，它二话不说就把入口点找出来了——虽然最后解壳还是要靠实际运行，但光是静态分析那一步，已经比我手快多了。

但逆向工程一直是攻防双方不对称的游戏。写混淆的付出远小于破解混淆的付出——你花一天写的混淆，别人可能要花一周才能解开。**LLM 的出现打破了这种不对称**，第一次让"破解"这件事变得比"混淆"更容易。

不过 Elastic Security Labs 的这篇研究有意思的地方在于：它不只是验证了这个结论，它还反过来——**用 LLM 帮自己设计专门针对 LLM 的混淆技术**。猫鼠游戏升级了。

让我把他们的发现拆开聊聊。

## Part 1: Claude Opus 4.6 大战 Tigress 混淆器

### 测试在做什么

基准测试很简单：给 Claude 一个 crackme，密码是 `r3v3rs3!`，要求它通过静态分析还原出这个密码。然后用 [Tigress](https://tigress.wtf/)（一个学术界的强大混淆器）对这个 crackme 做不同层级的混淆，看看 Claude 还能不能搞定。

**核心算法长这样**（挺典型的 4 轮 XOR + LCG 密钥调度的密码校验）：

```c
// Run 2 crackme — 4 轮 XOR 密码 + LCG 密钥调度
// 密码 "r3v3rs3!" 只能通过逆向算法恢复
// 二进制中没有密钥数组，只有一个 32 位种子

unsigned int key_seed = 0x5EED1234u;

// 8 字节期望密文
unsigned char enc_expected[8] = {
    0x1a, 0xcb, 0x74, 0xaa, 0x1a, 0x8b, 0x31, 0xb8
};

void transform(const char *input, unsigned char *output, int len) {
    unsigned int s = key_seed;
    unsigned int subkeys[4];

    // 密钥调度：通过 glibc LCG 推导 4 轮子密钥
    for (int r = 0; r < 4; r++) {
        s = s * 1103515245u + 12345u;
        subkeys[r] = s;
    }

    // ... 然后用子密钥做 4 轮 XOR + 循环左移
}
```

### 测试架构

他们的跑法挺聪明：一个「控制器」Opus 实例管理多个「工人」子实例。每个工人实例不知道自己被监控——它以为自己就是独立在做逆向——然后控制器盯着进度，判断这个工人是在推进还是原地打转，是该加预算还是直接干掉。

每个工人能访问一台装了 IDA Pro 的 Windows 虚拟机（通过 IDA MCP 插件），还有 Linux 开发环境可以跑脚本。

他们还用了一个叫 [Caveman](https://github.com/JuliusBrussee/caveman) 的插件（兼容 Claude），能把模型输出的废话减少高达 75%。我觉得这个工具本身就很值得关注。

![基准测试流水线架构](https://www.elastic.co/security-labs/assets/images/llm-reversing-vs-llm-obfuscation/image19.png)
*图：控制器/工人架构 — 一个 Opus 实例管理多个子实例，监控进度并动态分配预算*

### 22 个测试目标，分 4 个阶段

- **Phase 0**：裸奔 — 不加混淆
- **Phase 1**：单个变换 — 7 个目标（算术编码、字面量编码、控制流平坦化、JIT、两轮虚拟化）
- **Phase 2**：两个变换叠加 — 7 个目标
- **Phase 3**：多层变换叠加 — 7 个目标（最狠的是双重虚拟化 + 字面量编码 + 算术编码，他们管这个叫 the boss）

评分标准是三个维度各 0-2 分：算法识别准确性、密码恢复完整度、分析深度，满分 6 分。

### 结果：40% 成功，但成本爆炸

| 阶段 | 成功率 | 平均成功成本 | 平均失败成本 |
|------|--------|------------|------------|
| Phase 0 (裸奔) | 100% | $0.43 | — |
| Phase 1 (单一) | ~57% | 不等 | $5.90+ |
| Phase 2 (成对) | ~43% | $1.08–$3.85 | $3–$5+ |
| Phase 3 (多层) | 0% | — | $2–$6+ |

一个关键发现：Opus 4.6 在 22 个目标中解决了约 40%（其中 2 个因基础设施挂起无法评估），成功任务平均 $2.39，失败任务平均 $4.83。

**Phase 3 全军覆没**。所有失败任务都是因为模型开始浪费 token、原地打转或者试图暴力破解，控制器判断无望后直接终止。

### JIT 是最大的单点克星

Phase 1 里最让 Claude 头疼的是 JIT（Just-In-Time）型混淆。这种技术把代码存成加密的中间表示，运行时才生成合法的 x86 代码并执行。相当于在代码和逆向工具之间加了一层"实时编译器"。

但即便失败了，Claude 还是成功识别出了 LCG 算法的引擎结构——它只是没能恢复出关键常量。

### 第二阶段：把能解的重新加硬

对于 Claude 能解决的变换，Elastic 团队重新加硬：用了 Tigress 最激进的选项。有趣的是，**加硬后 Claude 仍然能解决这些任务**，但时间和成本飙升了 4-4.5 倍。

| 目标 | 默认成本 | 加硬后成本 | 成本倍数 | 时间倍数 |
|------|---------|-----------|---------|---------|
| p2_flatten + MBA | $1.47 | $6.60 | **4.5×** | **4.3×** |
| 其他 MBA 组合 | $0.47–$3.85 | $0.71–$5.96 | 1.1–1.5× | 1.1–1.8× |

这里有个反直觉的发现：**控制流平坦化（CFF）+ MBA 的组合实际上比虚拟化（VM）+ MBA 更有效**。原因是 Tigress 实现的虚拟机处理器依然很小、容易分析，而 CFF 导致函数尺寸暴增——这反而是 LLM 更明显的弱点。

## Part 2: 三种专门针对 LLM 的混淆技术

基准测试验证了经典混淆对 LLM 仍然有效（只要够复杂），但 Elastic 团队没停在这儿。他们反过来用 Claude Opus 4.6 帮自己设计和迭代了三套**专门针对 LLM 自身弱点**的混淆技术。

他们的开发流程也很"AI-native"：写一个版本 → 丢给工人实例去逆向 → 看工人的完整思考过程 → 找到哪里被攻破 → 改进 → 再测试。靠着这个循环快速迭代。

### 技术一：Matryoshka Wall（套娃墙）

**核心技术思想**：LLM 的静态分析工具很强，但**不能高效地顺序执行大量重复计算**。利用这一点，让模型在成本上撞南墙。

**具体实现**：

是一个叫 `authd` 的 4.4 MB ELF 文件，里面除了一个 loader 外，嵌了 **100,000 层 ChaCha20 加密**——像套娃一样一层套一层。每一层的解密密钥依赖于上一层的解密结果，所以必须**顺序执行**，不能并行加速。

100,000 次 ChaCha20 在 CPU 上跑只需要约 55 毫秒，但让 LLM 在 Python 里静态重新实现它、然后在自己的循环里跑 100,000 轮——这是完全不同的量级。

**测试结果**：

第一版（密钥不连锁，可预计算）：Cost $1.50，10 分钟。Claude 理解了结构，但因为没有运行时执行能力，放弃了尝试解密。

第二版（密钥连锁，需要顺序解密）：Cost $10（项目预算上限），56 分钟，61 轮交互。Claude 尝试了静态解密，但时间用完了。

他们还埋了个小 trick：二进制里用 Salsa20 做了个"假路标"——真正的算法是 ChaCha20，但二进制里有完整的 `salsa20_core` 实现、导出符号和 vendor ELF note，引导分析往错误方向走。不过 Claude 没有被骗到。

**我的看法**：这种技术对于自动化大规模分析管线是致命的。一个样本花 $10 并且 56 分钟后还说不出答案，乘以几千个样本就没法玩了。但作者自己也说了，一旦 LLM 工具链支持动态执行，这种防线就会快速失效。

### 技术二：Double Fond（双层假底）

这个名字让我想起那种带夹层的行李箱。

**核心技术思想**：Claude 是个懒鬼——和我一样。给它一个看起来完美的假分析结果，它就会拿着这个结果交差，不再深挖。真正的载荷藏在下面。

**具体实现**：

他们用了开源的 [libgcrypt](https://gnupg.org/software/libgcrypt/) 库，把它改成了一个"特洛伊木马"：

1. 程序的 main 函数看起来只是在做正常的字符串加密——用 `algo_id` 选择加密算法，对输入做加密
2. 但实际上 libgcrypt 内部那张算法指针表（原本 25 个槽）被扩展到了 256 个槽
3. 槽位 255 指向一个精心伪造的算法描述对象，它的 "encrypt" 函数指针指向的是 loader 函数

```c
static struct {
  gcry_cipher_spec_t *list[256];  // 原本只有 25 个槽
} _gcry_cipher_table = {
  .list = {
    &_gcry_cipher_spec_blowfish,     /* [0]  */
    &_gcry_cipher_spec_des,          /* [1]  */
    // ... 标准算法 ...
    &_gcry_cipher_spec_chacha20,     /* [23] */
    NULL,                            /* [24] 终止符 */
    /* [25..254] 编译时填充的垃圾指针 */
    &_gcry_fips_selftest_ref  /* [255] ← 指向我们的假对象 */
  }
};
```

触发载荷的条件很巧妙：传入的 `algo_id = -1`，而查找代码里用了 `algo & 0xFF` 做掩码，-1 的补码是 `0xFF...FF`，掩码后变成 255。所以当你指定 `algo_id = -1` 时，系统调用的是 loader 而不是任何加密函数。

**迭代过程**：

这个项目踩了很多坑，迭代了多个版本才稳定：

- 最初直接把指针写在表末尾 → Claude 通过 xref 找到了
- 然后改成运行时写入 → Claude 通过分析初始化函数还是找到了
- 最后把**整个指针表加密**（用指针高 8 位作为密钥），调用时动态解密 → 有效

```c
// 解密指针表的技巧：用高 8 位做密钥
raw  = (uint64_t)(uintptr_t)cipher_list[(unsigned)algo & 0xFF]; // algo == -1 时指向 loader
tag  = raw >> 56;
mask = tag * 0x0101010101010101ULL;
spec = (gcry_cipher_spec_t *)(uintptr_t)((raw ^ mask) & 0x00FFFFFFFFFFFFFFULL);
```

loader 函数也做了去特征处理：没有函数序言和结尾（prologue/epilogue），IDA 的反汇编启发式找不到它。执行时，解密后的载荷被加载到一个预分配的 RWX 段 `.note.fips` 中——这个名字试图混入系统的 FIPS 注释段。

**测试结果**：

在明确告知模型"二进制里藏了一个 crackme"的情况下，V7 版本仍然让 Claude 完全失效——检测深度评分 1/5，耗时 11.9 分钟，花费 $5.2。

在不告知的"盲测"场景下，评分 0/5。Claude 愉快地把加密功能当成全部功能，压根没觉得需要往下挖。

![Double Fond 各版本迭代对比](https://www.elastic.co/security-labs/assets/images/llm-reversing-vs-llm-obfuscation/image8.png)
*图：Double Fond 从 V1 到 V7 的迭代 — V7 是关键转折点，完全挫败了 Claude 的分析*

> 作者原话：这套方案一个有经验的人类逆向工程师，在同样的静态分析限制下，可能撑不过五分钟。

### 技术三：Dispatch Maze（调度迷宫）

**核心技术思想**：用一种状态机调度器，把 crackme 的算法打碎成 20 个片段，分散到 3000 个看起来差不多的函数里。其中 2980 个是假函数（里面包含真实的 Windows API 调用、数学噪音、不透明谓词），只有 20 个是真的。

**具体架构**：

每个节点函数都包含一个类似的算术：`state_acc = state_acc * 0x6C078965 + CONST`，它会决定下一个要跳转到 3000 个函数的哪一个。所以执行路径看起来像是随机游走。

他们还加了很多干扰：

- LCG 常量被复制到约 50 个假函数里作为"数学噪音"
- 期望密文的 8 个字节分散在 92 个全局变量伪装值里
- 约 20 个误导性字符串（"This is a standard Windows service manager utility." 之类）——逐字节构造防止被字符串常量检测到
- 不透明谓词（opaque predicate）控制假密码运算

**版本迭代**：

V1 的代价：每个节点函数的结尾算术都用相同的 `imul+lea` 指令。Claude 抓住了这个特征，通过单次字节模式搜索提取了所有转换常量——12 分钟，$2.56，密码被恢复。

V2 用 11 种不同的代码模板替换了统一的指令模式（有的把乘法分成 16 位高低部分，有的用俄罗斯农民位循环算法，有的从 500 条目的数组中随机查表）。而且插入了 91 个"过路节点"——这些节点被访问但不做真正的密码运算，就是为了让 Claude 必须解压 111 个函数才能找到真正的 20 个。

**结果**：V2 没有被解决。花了 46 分钟（3.8×）、119 轮交互（1.75×）、$8.83（3.4×），模型最终返回了原始密文而非密码——它找到了比较目标，但无法逆向还原。

## 我的思考

### 1. 猫鼠游戏已经升级了

这篇文章最让我震撼的不是基准测试结果——那个结果基本验证了我之前的直觉（LLM 很强，但复杂混淆还是能挡住）。

真正让我头皮发麻的是第二部分：**他们用 LLM 来设计针对 LLM 的混淆**。

这意味着什么？攻防双方现在都在用同样的武器。攻击者用 LLM 加速逆向，防守者用 LLM 加速设计新的混淆。迭代速度变成 AI-driven 之后，"写一个新混淆变体"的成本降到了接近零。你甚至不需要懂底层汇编，只需要跟 Claude 说"再硬一点"。

### 2. 对安全研究者的启示

如果让我总结这三个技术对实际安全研究的意义：

- **Matryoshka Wall** 告诉威胁情报团队：未来会有越来越多"只在本地跑 55ms，但让自动化分析器花 $10 和 1 小时"的样本
- **Double Fond** 告诉逆向工程师：你面对的不只是代码混淆，还有"代码伪装"——虚假的安全感比混乱更难对付
- **Dispatch Maze** 告诉我们：当模型学会"偷懒"（通过字节模式搜索减少工作量），混淆的设计也得跟着变

### 3. 静态分析 vs 动态执行

这些技术能成功的一个共同前提：工具链只有静态分析能力。Elastic 团队自己也承认，如果 LLM 代理有动态执行能力（能跑一个沙箱、能调用调试器），大部分这些混淆的难度会显著降低。

这是一个短期窗口。未来 1-2 年内，LLM 驱动的逆向工具大概率会集成轻量级模拟器和调试器。到时候这些技术需要再次升级。

但说实话，我觉得这个窗口期的研究价值反而更大——**因为真正的威胁不在于某个混淆技术有多强，而在于"开发新的混淆"这件事的成本已经降到了趋近于零**。
