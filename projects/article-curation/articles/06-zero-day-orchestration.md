# 零日漏洞发现不需要「前沿模型」——编排框架才是真正的核心能力

> 最近 Anthropic 发了 Mythos 报告，说他们的「前沿模型」发现了 1998 年 OpenBSD 的 27 年老漏洞。媒体渲染之下，零日发现似乎成了 Mythos 这种受限模型的专属能力。可事实真是这样吗？

Niels Provos 不这么认为。他做了个实验来验证——结果发现，真正关键的东西不在模型本身，而在编排框架。

而且 Provos 有个非常独特的身份：**1998 年 OpenBSD TCP SACK 实现（含那个 bug）的提交者，就是他自己。** 27 年前亲手写进去的 bug，27 年后用 AI 重新发现——这个故事本身就值得聊。

**⏱️ 阅读时间**：约 8 分钟

**🔧 涉及技术**：IronCurtain · FSM 编排 · AI Agent · 漏洞发现 · OpenBSD · GLM 5.1 · Open-Weight Models

## Part 1：IronCurtain 是什么

Provo 开发了一个叫 **IronCurtain** 的开源框架，核心是一个基于有限状态机（FSM）的编排系统。你可以用纯 YAML 定义任意的工作流，然后系统会按状态图自动推进。

在漏洞发现这个场景下，他构建了一个 `vuln-discovery` 工作流。这个工作流里有一个核心的 **Orchestrator** 代理——它自己不看源代码，而是维护一个**只追加（append-only）的执行日志**，根据日志内容决定下一步调度哪个专业代理。

日志 + 磁盘持久化让每个代理都能用干净的新上下文窗口启动，然后从磁盘恢复状态。代价是 token 消耗很大——跑一次 Opus 或 Sonnet 大概要 1000 万 token。

但这不是重点。重点是这种设计把「谁来决策」和「谁来执行」分开了，Orchestrator 只负责调度和路由，具体的分析工作交给下游的专业代理。这个架构本身不依赖任何特定模型。

## Part 2：复现 1998 年的 OpenBSD 漏洞

Provo 指向了那个自己 27 年前提交的 TCP SACK 代码。他用 Sonnet 4.6 做初始分析代理，让工作流先做静态分析，映射数据流和调用链。

一开始不太顺利。因为 IronCurtain 的安全容器没法原生启动 OpenBSD 虚拟机，代理只能做静态分析。它确实找到了 bug，但没法做 PoC（概念验证），报告交出来缺了最关键的执行证据。

Provo 没有放弃。他意识到一个关键设计缺陷：**一开始就用全量 VM 环境太重了，应该分层递进。**

于是他改进了工作流，引入了三层 harness 策略：
1. **单函数隔离 harness** —— 轻量级 fuzzing
2. **多组件 harness**
3. **全链路 VM 验证**

随后他用 Opus 4.6 + Claude Code 做验证。先让模型设计一个针对特定 C 函数的独立高性能 fuzzer，几秒钟内扫完输入空间。fuzzer 找到了精确的触发条件——**在 43 亿个序列号中，仅差 2 个序号，而且正好落在 32 位整数符号边界上。**

一旦参数锁定，再让模型构建 QEMU 驱动，在真实虚拟机里复现内核 panic。

> 43 亿分之一的概率，找到精确触发条件——这不是模型多聪明，而是编排系统让模型能把问题缩小到可解的空间里。

做完这次验证后，Provo 把学到的东西反馈进了 FSM 的提示词和日志机制。之后的工作流就再不需要人工干预了。

## Part 3：真正的零日发现

复现老漏洞只是热身。真正的考验是：这个编排框架能不能在没有人类引导的情况下，在广泛部署的现代软件里找到**从未被报告过**的漏洞？

### 案例一：Opus 4.6 发现媒体框架漏洞

`vuln-discovery` 工作流指向一个广泛部署的媒体框架，使用 Opus 4.6。Orchestrator 自动完成了发现、构建多组件 harness 来确认原语。验证最终 PoC 时遇到了一点内存环境问题导致触发条件被掩盖，在人工辅助优化 harness 后成功触发。

漏洞已上报上游维护者。

### 案例二：GLM 5.1 发现潜伏 18 年的整数截断漏洞

这个案例更炸裂。Provo 直接把 Anthropic 的 API 换成了 Z.AI 的 **GLM 5.1**（一个开源权重模型），通过 LiteLLM 网关做协议转换——**IronCurtain 和整个 FSM 编排层一行代码没改。**

GLM 5.1 完整驱动了整个发现过程。Orchestrator 读取追加日志，确定目标范围，调度到分层 harness 构建。模型自主隔离了一个**内存分配路径上的整数截断漏洞**，这个 bug 在代码里躺了 **18 年**。

为了做负责任的披露，Provo 手动验证了可利用性：用 Opus 4.7 确认了受控的堆越界读写原语。由于受影响库广泛部署在互联网基础设施上，这个漏洞被评估为高危远程风险。

### AUP 摩擦的真实案例

在确认严重等级时，Provo 需要构建一个完整 exploit。但 Opus 4.7 的安全策略拒绝了他的请求。

他把 exploit 开发拆成了**七个步骤**的精细计划。模型成功执行了前两步——第二步已经证明可以绕过 ASLR（地址空间布局随机化）读取基址指针——然后被 AUP 护栏强制中断，拒绝继续协作。

请注意：**这是防御者做负责任的漏洞确认，不是在搞破坏。** 但策略不分场景，一刀切地拦住了。

## Part 4：经济账和防御者视角

Provo 给出了一个非常直观的数字：

- **Sonnet 4.6**：单次审计约 **$30**（~1000 万 token）
- **Opus 4.6**：单次审计约 **$150**
- **GLM 5.1（Z.AI 托管）**：同样价格区间（每次约 2700 万 token，但单价低）
- **自托管开源模型**：前期投入后边际成本更低

几十到一百多美元审计一个代码库——这个价格意味着，一个防御组织一年的预算可以决定它「审计得起多少个库」。

而攻击者呢？他们不受任何限制：
- ✓ 没有 AUP 使用策略卡住敏感操作
- ✓ 没有 API 速率限制影响长时间运行
- ✓ 没有只对特定组织开放的前沿模型访问清单
- ✓ 完全可以在本地跑 uncensored 的开源模型

**这种不对称才是真正该担心的事情。**

## 我的思考

**1. 编排框架才是核心能力，模型只是执行者**

IronCurtain 的 FSM + 日志驱动架构，跟传统 AI 安全叙事说的「模型越强越能发现漏洞」完全是两个思路。Provo 的实验清楚地表明：只要你把编排做好，GLM 5.1 这种开源权重模型也能发现潜伏 18 年的零日漏洞。换一个更强的模型当然更好，但不是决定性的。

**2. 开源模型正在迅速追赶**

GLM 5.1 能在零修改编排层的情况下跑完整套工作流，这件事本身就说明了一点：开源模型的质量已经过了某个门槛。Provo 的原话特别好——"foundation model quality sets the floor for what orchestration can extract, but the open-weight result shows that floor is now low enough for commodity models to clear." 基底模型决定了编排能挖出来的上限，但开源结果证明这个下限已经低到普通模型也能跨过。

**3. AUP 摩擦对防御者不利**

那个七步拒绝的故事太有代表性了。在安全研究领域，工具永远面临双刃剑 debate——Metasploit、nmap、Burp Suite、AFL，每一个都经历过「会不会被滥用」的质疑。历史上给出的答案一直是一样的：**把工具交到防御者手里。** 现在也一样。在本地模型上，责任归于研究者本人——就像过去 25 年所有安全工具一样。
